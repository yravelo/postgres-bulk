# PostgreSQL Bulk 0.1.0 release notes

`0.1.0` is the first planned public release of PostgreSQL Bulk. These notes describe the inspected
release candidate; they do not claim that the artifacts are available from a remote repository.

## Requirements and installation

- Java 17 or newer; Java 17 and 21 are the supported runtime lines.
- Spring Boot 3.5.x, Spring Data JPA 3.5.x and Hibernate ORM 6.6.x.
- PostgreSQL 15–18 and pgJDBC 42.7.x within the published tested boundaries.
- A write-capable Spring transaction for bulk lookup.

Once publication is authorized and completed, consumers will depend directly on
`io.github.yravelo:postgres-bulk-spring-boot-starter:0.1.0`. These are the final approved
coordinates. The development repository exists and remains private; Central namespace
confirmation is complete (`io.github.yravelo` is owner-confirmed `VERIFIED`). Phase 16E selects
GitHub Actions Repository Secrets with a manual, exact-commit/tag-gated upload workflow; the real
Portal token, OpenPGP key, four secret values, tag, upload and publication remain intentionally
withheld external actions. See
[release readiness](release-readiness.md).

## Capabilities

- COPY-based bulk insert with assigned identifiers and explicit batch sizing.
- Temporary-table lookup for simple and composite keys, with input de-duplication and deterministic
  database-driven result semantics.
- Hibernate runtime mapping for supported field/property, embedded-ID, converter, enum and UUID
  mappings.
- Spring Data JPA repository fragments and Spring Boot auto-configuration with user back-off.
- Optional Micrometer observations, row counters and batch counters without requiring Actuator.

## Important semantics

COPY participates in the current Spring transaction. The library does not commit, roll back or
close framework-owned connections. A later outer rollback can undo a successful bulk call. Lookup
uses a temporary table and rejects missing or read-only transaction boundaries. There is no
automatic retry; callers own idempotency and retry policy.

## Known limitations

- Integration is for Spring Data JPA/Hibernate. Spring Data JDBC is not part of `0.1.0`.
- Spring Boot 4 and Hibernate 7 are unsupported.
- `NESTED` propagation is unsupported by the validated baseline.
- Generated identifiers are not synchronized back into input objects.
- COPY bypasses JPA callbacks, cascades and persistence-context management/refresh.
- Multi-table entity mappings are unsupported.
- There is no automatic retry or partial-write compensation.
- Lookup requires a write-capable transaction and its performance depends on schema, statistics and
  planner choices.
- Further COPY allocation optimization is future work; the current batch default is unchanged.
