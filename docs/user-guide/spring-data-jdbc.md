# Spring Data JDBC

## Getting started

Install the local `0.1.0-SNAPSHOT` and add only this direct postgres-bulk dependency:

```xml
<dependency>
  <groupId>io.github.yravelo</groupId>
  <artifactId>postgres-bulk-spring-boot-starter-data-jdbc</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

Declare a normal aggregate root and opt its repository into the bulk fragment:

```java
@Table("product")
public record Product(@Id UUID id, String sku, String category) {}

public interface ProductRepository
        extends CrudRepository<Product, UUID>,
                PostgresBulkJdbcRepository<Product> {
}
```

The supported Boot 3.5 line discovers the repository fragment and auto-configures the metadata
resolver when `DataSource`, `JdbcOperations`, `JdbcConverter`, `JdbcCustomConversions` and
`RelationalMappingContext` each have one effective candidate. `postgres-bulk.enabled=false`
disables that composition. A user resolver wins, and ambiguous candidates cause back-off rather
than order-based selection. The starter enables no repositories and creates no datasource or
transaction manager.

## Insert and result

```java
@Transactional
public BulkWriteResult importProducts(List<Product> input) {
    BulkWriteResult defaults = products.bulkInsert(input);
    BulkWriteResult explicit = products.bulkInsert(
        moreProducts(), BulkInsertOptions.ofBatchSize(5_000));
    return new BulkWriteResult(
        defaults.affectedRows() + explicit.affectedRows(),
        defaults.batches() + explicit.batches());
}
```

Input is consumed once with O(1) additional memory. Assigned IDs are copied. Generated numeric IDs
are omitted and generated by PostgreSQL, but are not returned or written into the input object.
Every row in one call must use the same assigned/generated metadata variant.

## Lookup

Simple and composite keys name exact physical columns:

```java
record ProductKey(String sku, String category) {}

BulkKeyMetadata<ProductKey> key = BulkKeyMetadata.of(
    ProductKey.class,
    List.of(
        ColumnMetadata.of("sku", String.class, ProductKey::sku),
        ColumnMetadata.of("category", String.class, ProductKey::category)
    )
);

@Transactional
public List<Product> findProducts(List<ProductKey> keys) {
    return products.findAllByBulkKey(keys, key);
}
```

Duplicates do not multiply results, missing keys return no row, null keys/components fail, and
result order is unspecified. Lookup uses a temporary table and therefore requires a write-capable
transaction.

## Transactions

- Fragment methods use `REQUIRED`; direct calls through the repository proxy create a transaction
  and outer transactions control commit/rollback.
- `REQUIRES_NEW` uses an independent physical transaction supplied by Spring.
- `NESTED` is supported only when a JDBC transaction manager for the same datasource owns and
  supports the savepoint.
- Non-empty calls through the delegate without a transaction are invalid.
- Insert and lookup reject logical or physical read-only transactions before COPY work.
- Multiple datasources, `JdbcOperations` or managers require explicit application selection.

The library never commits, rolls back, closes or reconfigures the Spring-owned connection.

## Mapping and lifecycle

Supported root values include standard scalars, UUID, `byte[]`, Java Time, enums, static custom
converters, embedded values and scalar-ID `AggregateReference`. Assigned IDs are fully supported;
generated numeric IDs are partial because values are not synchronized.

Collections/children, version, sequence IDs, callbacks, auditing, events and graph persistence are
unsupported. Always-quoted exact identifiers work, including quoted mixed case; plain mixed-case
identifiers that rely on PostgreSQL folding do not. See the complete
[mapping matrix](mapping-support.md).

## JPA and coexistence

The JDBC and JPA starters share core metadata contracts and the pgJDBC COPY/temporary-table engine,
but use different integrations:

| Concern | Spring Data JDBC | Spring Data JPA |
|---|---|---|
| Mapping source | `JdbcConverter`/Relational mapping | Hibernate runtime metamodel |
| Materialization | `EntityRowMapper` | Hibernate native query |
| Lifecycle bypassed | JDBC callbacks/auditing/children | JPA callbacks/events/cascades/context sync |
| Typical manager | JDBC transaction manager | `JpaTransactionManager` |
| Starter | `postgres-bulk-spring-boot-starter-data-jdbc` | `postgres-bulk-spring-boot-starter` |

Both starters can coexist with separate repositories and explicit infrastructure. A repository
combining both bulk fragments is unsupported, and separate local managers do not provide atomic
cross-store transactions.

## Limitations and future work

PostgreSQL and a pgJDBC-unwrappable connection are required. The operation is root-only, has no
retry, does not populate generated IDs and does not guarantee lookup order. Runtime schema/tenant
selection is **PLANNED**, not implemented; current schema comes from mapping metadata. No global
schema property is promised.

Run the [executable example](../../examples/spring-boot-data-jdbc/README.md) for a complete Boot
application using Docker Compose manually and Testcontainers in automated verification.
